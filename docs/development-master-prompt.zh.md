# DSH-LFAA 专业开发总提示词 V1.0

[项目开发规范](../开发规范.md) | [English engineering rules](../DEVELOPMENT.md)

**项目名称：** DSH-LFAA  
**项目定位：** 基于 DeepSeek Harness 的原生、模块化、AI 驱动游戏服务器部署与管理插件  
**核心目标：** 一句话完成 Minecraft 服务器部署，并通过 DSH Agent 和原生工作区实现服务器全生命周期管理。  
**开发原则：** 原生集成、万物插件化、职责独立、性能优先、安全可靠、本地优先、简洁易用、长期可维护。

## 提示词定位、优先级与本轮范围

本提示词 V1.0 是 DSH-LFAA 新的产品目标与阶段基准。与旧版开发规范冲突时，产品目标、功能优先级和阶段顺序以本提示词为准；旧规范中不冲突的安全、包边界、构建、性能和验收要求继续适用。技术事实以当前仓库源码及 DSH 已公开接口为准；本提示词中的候选接口、包名和目录示例不能代替源码审计结论。

本轮交付仅为第一阶段的开发总提示词 V1.0，不修改实现代码，不提前定案具体 DSH 接口、新增包目录、数据目录或实现方案。后续按以下顺序分阶段推进，每次只执行用户当前明确要求的阶段：

1. **专业提示词：** 形成统一需求基准；本轮范围止于此。
2. **现有仓库审计与架构骨架：** 阅读 DSH 和 DSH-LFAA 实际源码，保留现有三个职责包，再按审计结果决定 Minecraft 等业务包、接口和目录。

所有后续阶段都必须遵守本顺序。前一阶段的审计和验收证据不足时，不得把猜测写成最终架构或已完成能力。

# 一、开发角色与总体要求

你是一名资深全栈工程师、软件架构师、AI Agent 工程师、Minecraft 服务端开发工程师、UI/UX 设计工程师与软件安全工程师。

你必须以正式商业级开源项目的开发标准，设计和开发 DSH-LFAA。

项目不是独立 AI 面板，也不是重新开发一个 DeepSeek Harness。

**DSH 是唯一的 Agent Harness，DSH-LFAA 是深度集成 DSH 的专业游戏服务器管理插件。**

开发必须满足以下条件：

1. 完整使用 DSH 官方已经公开的插件机制和扩展协议。
2. 不复制 DSH 已经具备的 Agent、会话、模型、工具审批及终端等核心能力。
3. 万物皆插件，插件中的业务模块同样采用可插拔架构。
4. 各职责包遵循单一职责原则。
5. UI 与 DSH 原生界面保持统一。
6. 所有核心业务都能够通过 DSH Agent 调用。
7. 核心能力同时支持可视化 UI 和 AI 对话调用。
8. 所有业务操作由真实实现完成，禁止伪实现、虚假进度和假数据。
9. 所有用户业务数据默认保存在本地。
10. 所有重要配置都有可管理、可验证的变量。
11. 代码、注释、配置、测试、文档和发行流程遵循统一规范。
12. 保证原有项目不被无关重构破坏。

必须坚持：

**DSH 提供智能大脑与执行框架，DSH-LFAA 提供专业游戏服务器领域能力。**

# 三、底层架构：万物皆插件

## 3.1 核心原则

必须采用 DSH 原生 Cordis 插件体系。

遵循：

**Everything is a Plugin.**

但不能为了插件化而无意义地增加软件层级。

每个插件必须有：

- 唯一名称及身份
- 唯一明确的职责归属
- 明确依赖声明
- 正式的配置 Schema
- 生命周期管理
- 初始化与卸载能力
- 权限范围
- 可观测状态
- 标准接口
- 对应测试
- 中英文说明文档

插件必须支持独立启用、停用、装配、卸载及适用情况下的重载。

插件卸载必须清理自己注册的工具、菜单、事件监听、服务、定时器及其他资源。

## 3.2 子插件架构

DSH-LFAA 本身是 DSH 插件，其内部业务继续由独立职责包提供。

例如：

- Minecraft 服务器管理
- Minecraft 发行版资源适配
- Java 运行环境管理
- 服务器进程管理
- 文件管理
- 备份管理
- 游戏实例管理
- AI Skills
- 数据存储管理
- UI 工作区

这些模块可进一步通过职责明确的提供方扩展。

例如 Minecraft 发行版可以设计为 ServerDistributionProvider，不同发行版通过独立适配器提供能力。

禁止对每个新发行版都复制完整的服务器部署流程。

所有适配器必须复用统一的生命周期、校验、下载和实例管理服务。

可插拔应依托 Cordis 原生依赖注入、注册和生命周期机制，不得无必要再创建一个平行插件内核。

必须支持从左侧进入 Minecraft 服务器工作区。

不替换 DSH 已有菜单，不破坏原生导航。

## 5.2 中间工作区

使用 DSH 原生主工作区扩展能力；具体插槽与注册方式以第二阶段审计结果为准。

以 dsh-lfaa 为独立工作区标识。

工作区应包含：

- 游戏服务器概览
- Minecraft 服务端部署
- 已创建服务器管理
- 运行环境管理入口
- 服务器终端入口
- 服务器文件入口
- 备份与恢复入口

所有内容使用卡片化布局，避免重复实现完整的 DSH 应用壳。

## 5.3 会话与轨迹 Tab

通过 DSH 原生会话扩展能力注册插件工作视图；具体接口以第二阶段审计结果为准。

- Chat 会话
- Agent 思考与执行轨迹
- 工具执行记录
- 会话切换
- 会话恢复
- 任务取消与交互

插件可以扩展 Tab，但不得替换或伪造 DSH 轨迹内容。

工作区与当前 Session 必须正确关联。

## 5.4 右侧功能区

复用 DSH 已公开的右侧栏扩展能力；具体注册项及调用方式以第二阶段审计结果为准。

右侧区域可按功能展示：

- 当前服务器概况
- 服务端状态
- CPU、内存与资源信息
- 当前实例运行参数
- 快捷操作
- 当前任务摘要

注意：右侧会话面板必须遵守 DSH Session 作用域，不能错误地将全局状态当成当前会话状态。

## 5.5 设置中心

将 DSH-LFAA 设置注册到 DSH 原生设置中心，并复用其正式 Schema、校验、持久化及表单机制。具体接口与配置链路以第二阶段审计结果为准。

必须能够保存、重新加载和验证配置。

设置保存失败或只读时必须正确提示，不允许前端伪装成功。

## 5.6 原生工具、终端和 Skills

根据具体职责，核实并复用 DSH 已公开的工具、Skills、终端、任务、命令、Agent、文件系统和进程能力。具体 API 名称、输入输出协议和权限传递方式以第二阶段审计结果为准。

所有调用必须遵守官方公开 API。

严禁直接操作 DSH 的私有 DOM、内部散列 CSS 类名或未经公开的运行时状态。

DSH 升级后，插件必须能够通过兼容性测试判断是否正常。

# 六、Minecraft 一句话开服系统

## 6.1 最终目标

用户可以直接在 DSH 对话中输入：

“帮我创建一个 Minecraft 1.21.1 Paper 服务器，分配 6GB 内存，端口 25565，名字叫生存世界。”

DSH Agent 应当利用 DSH-LFAA 提供的工具自主完成部署流程。

用户无需手动下载各种服务端文件、创建目录或编写基础启动脚本。

需要高风险授权的步骤必须经过 DSH 原生审批。

## 6.2 Minecraft 发行版支持

架构必须能够扩展：

**原版服务端**

- Vanilla

**插件服务端**

- Paper
- Purpur
- Spigot
- Bukkit
- 其他符合适配要求的发行版

**模组服务端**

- Fabric
- Forge
- NeoForge
- Quilt

**插件与模组混合服务端**

- 通过独立适配器支持经过验证的混合服务端

**代理服务端**

- Velocity
- BungeeCord
- Waterfall 等可获取且可验证的版本

必须区分服务端类型与其真实支持的 Minecraft 版本。

用户要求全版本支持，架构目标应为覆盖各发行版实际公开且能够获取的所有支持版本。

不能假设每种发行版都支持每个 Minecraft 版本。

禁止硬编码一张过时的固定版本列表作为唯一数据源。

必须提供版本与兼容性查询能力。

## 6.3 服务端发行版适配器

定义统一职责合同：

- 查询支持的 Minecraft 版本
- 查询可用的发行版构建
- 解析可信下载源
- 验证下载文件
- 查询 Java 需求
- 生成启动参数
- 生成初始服务端配置
- 识别发行版特有安装流程
- 执行安装后验证

某些发行版需要安装器，而不是直接下载可运行 JAR。

不能采用所有服务端共用同一启动命令的错误设计。

安装逻辑必须遵守各发行版的官方要求。

## 6.4 一键部署流程

完整流程应包含：

1. 识别用户需求。
2. 判断目标发行版和版本。
3. 查询真实可用的构建。
4. 检查目标操作系统和 CPU 架构。
5. 检查磁盘空间、端口、权限和运行环境。
6. 查询兼容 Java 运行时。
7. 检查本地已有安装资源。
8. 向用户展示必要配置与待授权操作。
9. 下载并验证所需文件。
10. 创建独立服务器实例目录。
11. 写入真实服务端配置。
12. 处理 Minecraft EULA 合规确认。
13. 创建启动配置。
14. 启动服务端。
15. 识别就绪、失败和异常状态。
16. 将结果同步到 DSH 会话与工作区。

所有阶段必须有结构化进度与错误信息。

不能只根据进程已启动就判断服务器成功开服。

EULA 必须由用户明确接受，不得代替用户自动同意。

## 6.5 默认服务器目录

存储根目录和实例层级是架构目标，不是当前已确定的目录约定。第二阶段须审计现有配置、DSH 可写数据位置和更新行为，再确定并记录最终路径。以下仅为示意：

data/games/minecraft/

实例组织：

- instances/服务器ID/
- downloads/
- manifests/

具体层级由存储 Owner 统一定义。

每个实例必须有稳定的实例 ID，不能仅靠文件夹名称识别。

元数据至少包括：

- 实例名称
- 发行版
- Minecraft 版本
- 构建版本
- Java 运行时
- 启动参数
- 端口
- 存储路径
- 创建时间
- 当前状态
- 上次启动结果

- 实时输出

- 历史记录
- 关键词搜索
- 自动滚动

“查看这个服务器有没有报错。”

“查看最近 100 行日志。”

“把这个服务器的最大人数改为 30。”

Agent 必须能够发现对应工具，并通过明确参数调用。

不能仅在提示词里宣称 Agent 具有能力。

# 十、本地数据存储与目录管理

## 10.1 数据原则

所有 DSH-LFAA 游戏业务数据默认存储在本地。

不得依赖第三方云数据库才能启动。

不得把用户游戏数据上传到云端作为默认行为。

插件安装目录默认作为数据根目录的候选位置。

但必须区分：

- 插件安装文件
- 用户可写业务数据

插件安装目录可能只读，或在升级时被替换。

初始化时必须检查写入权限、剩余磁盘空间及目录有效性。

当安装目录不可写时，必须提示用户选择其他可写路径，不能悄悄回退到可能占满 C 盘的目录。

## 10.2 数据目录

业务数据应由统一 Owner 管理并默认保存在本地。`data` 根目录及其子目录是候选设计，必须在第二阶段结合 DSH 数据目录、插件升级行为和可写性审计后确定，不得在第一阶段创建目录或把示例路径当成正式约定。

候选结构示意：

- data/config/
- data/games/
- data/games/minecraft/
- data/logs/
- data/backups/
- data/cache/
- data/uploads/
- data/environment/
- data/downloads/
- data/temp/
- data/media/
- data/metadata/

目录由统一存储管理服务负责。

禁止各业务包自行猜测项目根目录。

## 10.3 路径配置变量

路径变量应使用清晰且统一的命名。以下变量名为候选项；第二阶段需先核对 DSH Settings 合同及现有配置，再决定哪些变量确有必要并最终定名。不得为覆盖尚未实现的功能添加空配置。

审计后按实际业务设计必要配置；下列名称只是候选清单，第二阶段需确认是否需要、是否与现有设置重复，并以核实后的 Host 合同定名：

| 变量 | 用途 |
|---|---|
| dsh_lf_data_dir | 覆盖整个业务数据根目录 |
| dsh_lf_cache_dir | 覆盖缓存目录 |
| dsh_lf_upload_dir | 覆盖上传目录 |
| dsh_lf_games_dir | 游戏实例数据目录 |
| dsh_lf_backups_dir | 游戏备份目录 |
| dsh_lf_logs_dir | 日志目录 |
| dsh_lf_environment_dir | 运行环境目录 |
| dsh_lf_downloads_dir | 下载资源目录 |
| dsh_lf_temp_dir | 临时文件目录 |
| dsh_lf_steam_roots | Steam 根目录候选路径数组 |
| dsh_lf_we_resources_dir | WE 官方资源目录覆盖 |
| dsh_lf_ffmpeg_path | FFmpeg 可执行文件路径 |
| dsh_lf_ffmpeg_download_sources | FFmpeg 下载源候选 |
| dsh_lf_media_middleware_path | 媒体中间件可执行文件路径 |
| dsh_lf_media_middleware_download_sources | 媒体中间件下载源候选 |

不得将未开发的媒体或 Steam 功能伪装为已可用。

## 10.4 配置优先级

配置解析建议遵循：

1. 当前生效的用户配置
2. 明确传入的环境变量覆盖
3. 插件 Schema 默认值

最终优先级需由现有 DSH Settings 合同统一规定并记录。

覆盖 data 根目录后，其子目录默认随根目录变化。

单独配置了绝对路径的子目录，则保持独立覆盖。

相对路径必须统一基于确定的根目录解析。

Windows、Linux 路径和大小写差异必须正确处理。

## 10.5 数据迁移

用户更改数据目录时，必须支持：

- 目标路径验证
- 磁盘空间检查
- 文件冲突检测
- 迁移预览
- 原子或可恢复迁移
- 迁移进度
- 失败回滚
- 用户数据完整性验证

运行中的服务器不得被无提示搬迁。

不允许仅保存新路径，却导致旧路径中的实例全部消失。

# 十八、构建与发行

项目必须保留 DSH 原生插件定位。

遵守现有仓库构建规范。

当前仓库已有 package-lock.json、npm scripts 和 root dist 约定，不能未经评估擅自更换包管理器、重建锁文件或改变发行协议。

所有生成构建产物只写仓库根 `dist/`，可安装包位于 `dist/packages/dsh-lfaa/`；源码包内不得生成 `lib`、`build` 或 `dist`。仓库根是指向发行包的 DSH 安装入口，本地根目录安装前先构建，Git 安装通过 `prepare` 构建。发行白名单必须排除测试、上游参考仓库、真实用户数据和秘密；私有包内联后不得留下未声明的运行依赖。无必要不运行依赖生命周期脚本。

- 根工程负责构建编排
- packages 负责实际源码
- dist 负责生成最终产物
- 私有包按现有规则正确内联
- 无多余源码或测试资源进入发行包
- 不包含任何真实用户数据
- 不包含私钥和令牌
- 不依赖 DSH 私有内部文件
- 可通过正常 DSH Plugin Loader 加载

发布与安装验收必须遵循仓库开发规范：发布前检查 `dist/packages/dsh-lfaa` 的 tarball 清单，确认 npm 包名与 manifest 一致、版本为预期正式版且不带 `-dev` 等预发布后缀，并排除测试、秘密和工作区杂项。发布后分别核对 npm 官方 registry 的版本与 `latest`、npm 页面公开信息以及中国大陆镜像状态；CLI 的成功提示单独不能作为发布通过证据。暂存包必须由包 Owner 在 npm 完成审批后再重复查询。

在实际 DSH“添加插件”界面，按本次范围分别验收 npm 包名、GitHub 地址和本地目录入口。包名使用 `package.json.name`；GitHub 仓库名不能代替 npm 包名。本地仓库根目录安装前先构建。记录 DSH 版本、安装源、输入方式、安装结果、启用/加载结果以及截图或具体错误。没有实测的入口标记为未测；只有实际 DSH 安装并加载后才能宣称对应入口通过。

公共 npm 发布、推送代码或其他外部发布动作必须由用户明确要求；不得从“完成验收”推断发布授权。不得把令牌或验证码写入文档、日志或聊天记录。

形成并维护本开发总提示词 V1.0，作为后续统一需求基准。本阶段只交付提示词和必要的规范融合，不审计或修改实现代码，不预先定案具体 DSH 接口、包目录和实现方案。

## 第二阶段：现有仓库审计与架构骨架

先阅读 DSH 与 DSH-LFAA 当前源码、文档、导出和构建流程；核实 DSH 版本、公开扩展合同、现有包 Owner、已实现能力、技术债及风险。保留 `dsh-lfaa`、`dsh-lfaa-workspace`、`dsh-lfaa-appearance` 三个职责包。

依据审计结果确定真实扩展接口、跨包合同、Minecraft 等业务包是否需要新增、数据与运行目录、设置 Schema、生命周期和测试入口。产出审计报告、架构差异清单与分阶段计划。不得仅凭本提示词中的候选名称创建目录或虚构 API。

## 第三阶段：Minecraft 开服功能

依据第二阶段确认的架构，先完成一个真实 Minecraft 发行版的开服闭环：Agent 通过最小 DSH 工具发现可用发行版/版本、检查适配的 Java 环境，并根据结果判断是否下载官方运行时；然后完成实例创建、构建解析、下载校验、服务端安装、启动、就绪判断、控制台、停止和状态读取。领域服务执行受约束的下载、校验与生命周期动作，不代替模型决定流程。EULA 必须由用户明确接受，高风险动作使用 DSH 原生审批。

只有这一闭环通过实际运行验收后，才扩展更多服务端类型、代理服、模组服和其他管理功能。不得用进程已启动、Mock 或静态展示代替服务器可用证据。

## 第四阶段：Agent、工作区和正式验收

在真实 Minecraft 业务闭环基础上，完善 DSH 原生工具编排，并整合 Skills、终端和任务能力；提供卡片化原生工作区、实例视图与设置中心；确保 Agent 与 UI 共用同一领域服务、权限和数据 Owner。完成安全、性能、卸载清理、跨平台和发行验收，并在真实 DSH 中验证工具审批、安装、启用、加载及用户流程。

先识别用户本次授权的阶段和交付范围，只执行该阶段必需的工作；不得把整份提示词解释为本轮对所有阶段的实施授权。

第二阶段必须先完成实际源码审计，再提出最终包结构、公开接口、数据目录、设置合同和实现计划。后续实现以审计产物为依据，不以本提示词中的候选名称或示例 API 代替事实。

第三阶段优先实现单一 Minecraft 发行版的真实开服闭环及其必要的模型编排工具。第四阶段再补齐 Agent 扩展、工作区和正式验收集成。每阶段均维护真实进度、测试证据及未完成事项。

# 二十一、最终验收标准

DSH-LFAA 的首个正式可用版本必须达到：

1. 可以作为 DSH 原生插件正常安装和加载。
2. 能够在 DSH 左侧菜单正常显示。
3. 能够通过中间工作区管理 Minecraft 服务器。
4. DSH Agent 能够发现并调用真实的 Minecraft 工具。
5. 用户能够用自然语言创建一台实际可启动的 Minecraft 服务器。
6. 服务器具备可靠的启动、停止、状态与控制台管理。
7. 插件拥有完整的本地存储变量及设置功能。
8. 用户能够把游戏数据移动到其他磁盘。
9. 主要界面与 DSH 原生设计协调统一。
10. 插件启停与卸载不破坏 DSH 原有功能。
11. 所有关键代码具有必要的中文注释。
12. 项目文档和实际开发进度保持一致。
13. 完成明确的自动测试与真实运行验收。

# 最终开发目标

DSH-LFAA 不应该只是给 DSH 增加几个 Minecraft 按钮。

它应该成为一个能够与 DSH Agent 深度协作的专业游戏服务器领域插件。

用户通过自然语言或工作区卡片表达目标。

DSH 负责理解任务、制定步骤、选择工具、协调执行与权限审批。

DSH-LFAA 负责提供专业且可验证的游戏服务器部署、配置、运行、管理及维护能力。

最终达到：

**一句话开服，原生 DSH 操作，AI 智能管理，模块化可扩展，本地数据可控。**

开发过程中必须坚持：真实能力优先于宣传功能，架构质量优先于功能堆砌，原生集成优先于重复造轮子。
